أضف نظام الفوترة الإلكترونية (المرحلة 1 - ZATCA Simplified E-Invoicing) لمشروع Musk Ellolo. هذا النظام يُنشئ فاتورة إلكترونية متوافقة محليًا فقط - بدون إرسال فوري لأي منصة خارجية (هذا مو متطلب بالمرحلة 1).

## المتطلبات الرسمية الإلزامية لصيغة الفاتورة (Simplified Tax Invoice)

كل فاتورة يجب أن تحتوي على الحقول التالية:
- اسم البائع الكامل (مسك اللولو / Musk Ellolo)
- الرقم الضريبي للبائع (VAT registration number) - أضفه كمتغير بيئة VAT_REGISTRATION_NUMBER يُقرأ من process.env
- تاريخ ووقت إصدار الفاتورة (timestamp دقيق)
- رقم تسلسلي فريد للفاتورة (Invoice sequence number - تسلسلي لا يتكرر ولا ينقطع)
- إجمالي المبلغ شامل الضريبة (VAT inclusive total)
- إجمالي مبلغ ضريبة القيمة المضافة (VAT amount) بشكل منفصل
- **QR Code** يحتوي على البيانات أعلاه مُرمّزة بصيغة TLV (Tag-Length-Value) ثم Base64 - هذا التنسيق محدد رسميًا من ZATCA، ابحث في الكود المصدري المفتوح المتاح لمكتبات zatca qr code generator إن وجدت حزمة npm جاهزة تدعم توليد QR بصيغة TLV/Base64 المطلوبة (مثل حزم مفتوحة المصدر لـ ZATCA phase 1 QR)، واستخدمها بدل بناء الترميز يدويًا لتقليل الأخطاء

## التطبيق

1. أضف جدول جديد: tax_invoices
   - id, order_id (FK إلى storefront_orders، nullable إن كانت فاتورة يدوية غير مرتبطة بطلب متجر)
   - invoice_number (نص تسلسلي فريد، مثل INV-000001)
   - issue_datetime (timestamp)
   - seller_name, seller_vat_number
   - subtotal, vat_amount, total_amount
   - qr_code_data (النص المُرمّز الناتج بصيغة Base64)
   - created_at

2. عند إتمام أي طلب بحالة payment_status = paid (سواء من متجر العملاء أو محدّث يدويًا من الأدمن)، أنشئ سجل tax_invoice تلقائيًا مرتبط بالطلب.

3. Endpoint جديد: GET /admin/invoices (صلاحية "invoices":"view" - أضفها لجدول admin_permissions) يعرض قائمة الفواتير مع بحث برقم الفاتورة أو رقم الطلب.

4. Endpoint: GET /admin/invoices/:id/qr يرجع صورة QR code (كـ SVG أو PNG) قابلة للطباعة على الفاتورة.

5. واجهة: أضف قسم "الفواتير الضريبية" بالقائمة الجانبية للأدمن، يعرض جدول بكل الفواتير مع رقم الفاتورة، الطلب المرتبط، المبلغ، التاريخ، وزر لعرض/طباعة QR.

6. مهم: لو VAT_REGISTRATION_NUMBER غير موجود بمتغيرات البيئة، أرجع خطأ واضح عند محاولة إنشاء فاتورة بدل فشل صامت أو توليد فاتورة ناقصة.

## اختبارات

اكتب اختبارات تتحقق من:
- توليد رقم فاتورة تسلسلي فريد لكل فاتورة جديدة (بدون تكرار أو انقطاع بالتسلسل)
- توليد QR code صحيح يحتوي كل الحقول المطلوبة
- رفض إنشاء فاتورة لو VAT_REGISTRATION_NUMBER غير مُعرّف
- عدم تكرار إنشاء فاتورة لنفس الطلب مرتين

طبّق الـ schema (pnpm --filter @workspace/db run push)، شغّل pnpm run typecheck، واعطني ملخص دقيق بالملفات المعدّلة والاختبارات - وبصراحة تامة إن كانت صيغة QR code TLV/Base64 مطابقة فعليًا للمواصفة الرسمية أو تحتاج مراجعة يدوية إضافية مني قبل الاستخدام الفعلي.
