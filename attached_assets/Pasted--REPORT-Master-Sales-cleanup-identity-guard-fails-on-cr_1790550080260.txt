## Conclusion

Comparing this against your review file (`master-sales-journals-review-2026-09-27.csv`) row by row: the set of row/barcode/month identifiers is identical — same 82 original spreadsheet rows, same three gaps (`row-1`, `row-11`, `row-50` absent from both). The imported content matches exactly.

The only difference is the database-assigned `id` primary key: in our production database these 82 rows happen to occupy `id` 1–82 (first-ever writes to an empty table), while your reference environment shows them as `id` 79–160. `id` is a local auto-increment sequence — it is not portable identity between separate database instances, the same lesson as the earlier product slug/SKU mismatch.

The cleanup script's first guard hashes `id::text || ':' || source_id` and compares it to a constant (`4c187b5979e2469f9682d060f5bdeab4`) computed in your environment. That comparison will fail against any database whose `id` numbering differs from yours, even when the content is byte-for-byte identical — which is exactly what happened here.

## What we need

A corrected identity guard (and the restore script's equivalent check, if it has the same pattern) that establishes identity from `source_id` alone — or its parsed `row`/`barcode`/`month` components — plus the row count, **without** including the database-local `id` column in the hash. Every other safeguard should stay exactly as strict: count = 82, the status/format/reversal checks, the FK and trigger checks, and the exact debit/credit total (141896.5843 SAR) — none of those depend on `id` and none of them have been shown to have any problem.

Note: execution stopped at this first identity check, so the later checks (status/format, dependent row counts, FK/trigger safety, exact amount totals) have not yet been exercised against production. They'll still run as an independent second layer of verification once the identity check itself is corrected — nothing about them is in question yet, they just haven't had the chance to run.

We are not modifying this script ourselves. No deletion will be attempted until a corrected version is provided.
